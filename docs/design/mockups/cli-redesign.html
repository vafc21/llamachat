6 Concrete Defects (Found by Running the CLI)

1. Theme picker misaligned
Selected row renders ❯ Dark at one indent with hint pushed right. Light and Auto are centre-aligned. Three rows don't share a column.
2. Slash popup truncates
/permissions View or change tool permissions / — cuts off mid-word at the popup edge, no ellipsis. Popup width doesn't fit its own content.
3. Popup bleeds onto text
Popup doesn't clear its background — live text shows through: ╮ith gemma2:9b-instruct-q8_0 bleeds out the side.
4. Alternate screen eats history
ratatui::init() enters the alternate screen. On exit, the entire session vanishes from scrollback. Claude Code and Codex both deliberately don't do this.
5. Palette contradicts the app
CLI is warm llama tan (#E8B066) + soft cyan. Desktop app is #4d7cff on #0d0d12. Two different products. Tier badges run a five-hue rainbow — opposite of the one-accent rule.
6. Empty box stretching
Models pane is 27 rows tall for 13 items. Heavy ┌─┐ borders everywhere. Most of the screen is empty box interior.

Three Design Directions

All three remove the alternate screen, unify the palette with the desktop app, and fix the 6 defects above. They differ in layout philosophy.

A — Inline (Claude Code style)

$ llamachat LlamaChat v0.4.0 · local-first · zero telemetry ❯ gemma2:9b-instruct-q8_0 Smart · ~62 tok/s . ▌ llama ▌ Here's a summary of the auth middleware. The token validation ▌ pipeline has three stages: decode, verify, and refresh. ▌ I found the refresh timer is hardcoded to 5 minutes — this should ▌ be configurable. ▌ ⎿ shell · find src -name '*.ts' | xargs grep refreshTimeout ▌ src/auth/middleware.ts:42: const REFRESH_TIMEOUT = 300; ▌ src/auth/config.ts:5: refreshTimeout: 300, ▌ src/auth/types.ts:8: refreshTimeout?: number; ▌ Both occurrences. Want me to extract it to config? ▸ create a configurable refresh timer

How it works: No TUI framework — crossterm raw mode for line editing only. Everything else is println!. Output scrolls naturally and survives the session. The input line sits at the bottom with a ▸ prompt. Model responses stream in with a ▌ gutter. Tool calls render inline. / commands are just typed words that match a prefix table — no popup needed.

What Codex does: Codex's TUI is a full ratatui app module but its core render loop pushes lines through chatwidget in a bottom_pane — it's still a full-screen TUI. The inline approach is closer to Claude Code's architecture (Ink/React streaming to the terminal, not taking over the screen).

How it works: Uses ratatui but renders to the main screen (not alternate — use Ratatui::raw_mode with custom backend that writes to stdout). This is closer to what Codex does with its bottom_pane and inline diff rendering.

The Fix (4 changes)

1. Register desktop as a model-visible tool. Add it to the tool registry in the agent loop so the model sees take_screenshot as an available action and can decide to call it.

2. Send the image bytes to Ollama. After desktop.rs captures to /tmp/llamachat-screenshot-*.png, read the file as base64 and include it in the next /api/chat request's images array. Ollama's API supports this natively — it's the same format as the OpenAI vision API.

3. Resize before sending. Use the image crate to scale screenshots to max 1568px on the longest edge before base64 encoding. This keeps token usage reasonable (a 4K screenshot is ~20K tokens raw; at 1568px it's ~4K).

4. Self-exclusion. On macOS: SCContentFilter to exclude the app's own windows from screen capture. On Windows: SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE). On Linux: Wayland's security model already prevents one client from capturing another's surface without the compositor — on X11 this is harder and may require the app to minimize itself before capture.

For Cowork mode specifically (your requirement: "takes a picture and can do real commands like move your mouse and type something"), this is the standard Claude Computer Use loop — screenshot → model sees it → model issues click/type/key actions → screenshot again. The desktop capture + computer control tools already exist; the missing piece is sending the screenshot to the model and letting it decide what to do next. The loop would be ~2s per cycle (capture + API round-trip) on local hardware.
